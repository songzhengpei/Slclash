# Android 网络恢复时的连接清理（beta 实验）

## 背景与边界

2026-10-28 的公共 Wi-Fi 现场中，认证前 Android HTTPS 探测出现证书信任链失败；认证完成、网络恢复验证后，ChatGPT 仍停留在 SSL 错误页。此时通过手机代理新建的相关域名 TLS 握手均成功，只重启 ChatGPT 后错误页消失。

这支持排查网络恢复后的应用/连接状态，但没有取得 ChatGPT 失败连接的证书，也未证明当天另一次流量网络故障有相同原因。本变更是 beta 上可观察的恢复实验，不宣称已修复 ChatGPT 所有 SSL 报错。

## 行为

继续使用现有“切换时关闭连接”开关，由 Android 原生服务处理，后台生效。

原有 Wi-Fi / 流量网络切换清理保留，增加以下事件：

- 同一物理网络完成公共 Wi-Fi 认证。
- 已验证网络失去验证后，再次恢复验证。
- 同一网络句柄下，本机 IPv4 地址集合改变。
- 已知网络暂时不可用后恢复，即使句柄没有改变。

触发时先调用现有 `resetConnections` 重置 DNS 解析器传输连接，再调用 `closeConnections` 关闭已跟踪的业务连接。每次清理记录原因和两个调用的结果，不记录域名、IP 或聊天数据。

重复能力回调、信号强度变化、地址排列变化、普通应用前台刷新，以及网络初次验证成功均不会单独触发清理。关闭自动清理或会话未运行/暂停时，只更新观察基线，不断开连接。

网络验证历史在原生观察队列中累计恢复序号。即使中间的认证状态通知被合并，后续快照仍带着恢复事件；显式刷新也保留该网络的历史。远端消费者只消费一次变化，不添加轮询或定时断线。

智能暂停仍按物理网络 IP/CIDR 判断，可信局域网无需获得互联网验证。这里没有修改选网优先级、VPN 路由、DNS 配置或节点切换策略。

## AnyTLS 限制

`closeConnections` 关闭业务流，不等同于清空 AnyTLS 的底层复用会话；`resetConnections` 也仅重置解析器传输连接。直接调用 AnyTLS 适配器的 `Close()` 会终止客户端，不能作为可复用的网络重置 API。

第一轮不修改协议层，避免将“补触发时机”和“改会话复用”混在同一实验中。若新记录显示这些清理动作已成功，但故障仍复现，再针对 AnyTLS 设计可重建会话的接口并做同节点对照。

已经显示的 ChatGPT 安全错误页可能仍需用户重启应用；SLClash 的连接清理不能保证第三方应用自动退出该页面。纯流量环境里没有网络状态、地址或节点变化的故障，仍需补充证据，不能通过前台切换或周期性断线覆盖。

## 验证

自动测试覆盖：

- 同一 Wi-Fi、地址和 DNS 下，认证完成只触发一次。
- 中间状态通知被合并后仍识别恢复。
- 验证丢失期间不清理，恢复后清理一次。
- Wi-Fi / 流量切换、同句柄地址更新、短暂无网恢复。
- 重复回调、地址排列及前台刷新不清理。
- 开关关闭、非活跃会话、会话停止后重建基线。
- 无互联网的可信局域网仍保持已知物理网络语义。

设备验收应保持同一节点，在公共 Wi-Fi 的认证前后检查恢复日志，随后验证新建 TLS/业务连接；同时观察已有下载或视频是否出现频繁中断。仅看到 ChatGPT 页面正常不足以证明此次恢复逻辑已触发，需核对原因日志。不要通过绕过证书校验验证效果。
